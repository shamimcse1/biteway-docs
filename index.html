Biteway Documentation

📘 Introduction

Biteway is a white-label food delivery platform. You run it on your own server, under your own brand:

  • Backend and admin panel (Laravel): the REST API for the apps, the admin panel at /admin, and a browser installer at /install.
  • Customer app (Flutter, Android and iOS): customers browse restaurants, order for delivery or pickup, pay, and follow their order on a live map.
  • Rider app (Flutter, Android and iOS): riders go online, accept deliveries, navigate to the restaurant and the customer, and see their earnings.
  • Restaurant app (Flutter, Android and iOS): restaurants take orders, run a kitchen display, manage tables and bookings, and use a quick POS.

The Customer Website and the Restaurant Portal are add-ons, sold as separate items with their own documentation.

Try Biteway before you set it up. The demo data resets every hour, and deleting, settings, keys, admins and payouts are switched off there.

Setup order

  1. Install the backend on your server with the browser installer (Installation).
  2. Start the background tasks: the cron job and the queue worker (Deployment).
  3. Set up the platform in the admin panel: your brand, areas and delivery zones, fees and commission, and the services you use (payments, maps, Firebase, and the text message provider for sign-in codes, which a live site needs before anyone can sign in to the apps).
  4. Build the apps with your name, logo and backend address, and publish them on Google Play and the App Store.
  5. Go live after the checklist in Deployment.

🧭 Installation

This section installs the backend and admin panel. Most hosts can use the browser installer; the terminal install at the end is for servers you control with SSH.

Before you start

You need:

  • A server that meets the requirements. The installer checks PHP and its extensions for you.
  • An empty MySQL or MariaDB database with the utf8mb4 character set, and a database user that can use it.
  • A domain or subdomain for the backend, for example api.your-domain.com, with HTTPS. The apps' release builds only connect to an https:// address, and the admin panel's sign-in cookie is only sent over HTTPS.
  • Composer 2 and Node.js 20.19+ or 22.12+ with npm, either on the server or on your own computer.
  • An account with a sign-in code provider: Twilio, BulkSMSBD or Firebase Phone Authentication. Customers and riders sign in with a code sent to their phone, and on a live site (APP_ENV=production, which the installer sets) the test provider that only writes codes to the server log is refused.

Testing without HTTPS? On your own computer (localhost or 127.0.0.1) everything works over http://. On any other http:// address, set SESSION_SECURE_COOKIE=false in .env after installing, or you will not be able to sign in to the admin panel. Set it back to true once the site has HTTPS.

1. Install the packages

The package ships without the vendor/ and public/build/ folders: you create them in this step. In the main/biteway-backend/ folder, run:

composer install --no-dev --optimize-autoloader
npm ci && npm run build

If your host has no terminal, run these two commands on your own computer, then upload the whole biteway-backend folder, including the new vendor/ and public/build/ folders.

npm run build also builds the styles and scripts of every add-on installed in addons/. After you install or update an add-on later, run it again.

2. Upload and point the domain at public/

  1. Upload the biteway-backend folder to your server, for example to /var/www/biteway-backend.
  2. Point your domain's web root (document root) at biteway-backend/public, never at biteway-backend itself. Everything outside public/ must stay out of reach of the web.
  3. Make storage/ and bootstrap/cache/ writable by the web server. On most Linux servers:
cd /var/www/biteway-backend
chown -R www-data:www-data storage bootstrap/cache
chmod -R 775 storage bootstrap/cache

Use your web server's user instead of www-data if it differs (for example nginx or your cPanel account).

3. Run the browser installer

Open https://your-domain/install. Every other page leads there until Biteway is installed.

  1. Server requirements: every line must show a green check. If one fails, fix it (or ask your host), then reload the page.
  2. Platform: your platform's name, and the URL the backend is reached at, for example https://api.your-domain.com.
  3. Database: the host, port, database name, user and password of the empty database.
  4. Super admin: the name, email and password of the first administrator. The password needs at least 8 characters, with letters and numbers.
  5. Currency: the platform currency. Every price, fee and payout uses it, and it can only be changed before the first order.
  6. Press Install. It creates the database tables, the Super Admin and the starting settings, and writes your .env file. This takes up to a minute.

When it finishes, the installer switches itself off: /install no longer opens.

4. After installing

  1. Add the cron job and start the queue worker shown on the last page. Without them, orders are not dispatched to riders and notifications are not sent. Deployment explains both.
  2. Sign in at https://your-domain/admin with the Super Admin email and password you chose.
  3. Open Health in the admin panel. It shows whether the scheduler and the queue worker are running.
  4. Open Setup assistant (under Super Admin, or from the dashboard's go-live checklist). It takes you through branding, currency, maps, sign-in codes, push notifications, payments and email one step at a time, and tests each service live (Admin panel). Set up the sign-in codes step first: until a provider is chosen, nobody can sign in to the customer and rider apps on a live site.

Terminal install

On a server with SSH, you can install without the browser:

cd /var/www/biteway-backend
composer install --no-dev --optimize-autoloader
npm ci && npm run build
cp .env.example .env

Edit .env: set APP_URL, the DB_ lines, ADMIN_NAME, ADMIN_EMAIL and BITEWAY_CURRENCY. Then run:

php artisan key:generate
php artisan migrate --seed --force
php artisan storage:link

If ADMIN_PASSWORD is empty, the seeder creates a random password for the Super Admin and prints it once. Copy it, sign in, and change it under your profile. Then add the cron job and the queue worker as described in Deployment.

Sample data for a trial

A normal install starts empty. To look around with sample restaurants, menus and orders, install a separate test copy with APP_ENV=local in .env before running php artisan migrate --seed. It adds three demo restaurants in Austin, Texas, with menus, photos and pricing, and switches on every feature under Settings → Extras with an example for each (Extras). Never use APP_ENV=local on your live platform.

⚙️ Deployment

How to run Biteway on a live server: the web server, the background tasks, the optional VPS extras (Redis, live updates, search, cloud storage and video conversion), email, the third-party services, going live and updating.

Web server

The domain's web root must be biteway-backend/public. A VPS (for example Ubuntu with Nginx or Apache) is recommended: Biteway runs a background worker all the time, which shared hosting often does not allow.

Nginx

A typical site file (/etc/nginx/sites-available/biteway). Change the domain, the folder and the PHP-FPM socket to match your server:

server {
    listen 80;
    server_name api.your-domain.com;
    root /var/www/biteway-backend/public;
    index index.php;
    client_max_body_size 20M;

    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }

    location ~ \.php$ {
        include fastcgi_params;
        fastcgi_pass unix:/run/php/php8.4-fpm.sock;
        fastcgi_param SCRIPT_FILENAME $realpath_root$fastcgi_script_name;
    }

    location ~ /\.(?!well-known) {
        deny all;
    }
}

Then add HTTPS, for example with Let's Encrypt: sudo certbot --nginx -d api.your-domain.com.

Apache

public/.htaccess is included. Enable mod_rewrite and allow the file to work (AllowOverride All for the public folder), then point the virtual host's DocumentRoot at /var/www/biteway-backend/public.

Shared hosting (cPanel)

  1. Set the domain's document root to biteway-backend/public (in cPanel: Domains, then Manage).
  2. Choose PHP 8.4 or newer under Select PHP Version or MultiPHP Manager, and turn on the extensions the installer lists.
  3. Add the cron jobs below under Cron Jobs. Use the full path to PHP that your host shows (often /usr/local/bin/php).
  4. Make sure public/storage exists, so uploaded photos show. Many shared hosts block PHP's symlink(), so php artisan storage:link can fail there. In that case run ln -s ../storage/app/public public/storage from the biteway-backend folder in cPanel Terminal.
  5. Enter the site URL in the installer in full, with https:// (for example https://api.your-domain.com).

Cron job and queue worker

Biteway needs both. You can check them at any time under Health in the admin panel.

The cron job runs the scheduler every minute. The scheduler dispatches orders to riders, expires unpaid orders, closes group carts nobody placed in time, checks ready food waiting for pickup, sends booking reminders, starts scheduled broadcasts and runs nightly checks. Add this line to the crontab of the user that owns the files (crontab -e):

* * * * * cd /var/www/biteway-backend && php artisan schedule:run >> /dev/null 2>&1

The queue worker sends notifications and push messages and handles payments and other background work. It also sends broadcasts, in batches of 500 people. It must run all the time:

php artisan queue:work --queue=dispatch,notifications,payments,default

On a VPS, keep it running with Supervisor, with one program for each long-running process. Create /etc/supervisor/conf.d/biteway-worker.conf:

[program:biteway-worker]
command=php /var/www/biteway-backend/artisan queue:work --queue=dispatch,notifications,payments,default --sleep=3 --max-time=3600
user=www-data
numprocs=1
autostart=true
autorestart=true
stopwaitsecs=3600
redirect_stderr=true
stdout_logfile=/var/www/biteway-backend/storage/logs/worker.log

Then run sudo supervisorctl reread && sudo supervisorctl update.

  • More orders, more workers: raise numprocs (for example to 3) and add process_name=%(program_name)s_%(process_num)02d. Each worker takes the queues in the same order, so dispatch and notifications go first.
  • Other long-running processes each get their own [program:...] block in their own file, so you can restart one without the others: a live-updates server, Reverb or Soketi (Live updates on a VPS), and Meilisearch (Search with Meilisearch), when you use them.
  • After every update or .env change, run php artisan queue:restart. The workers finish the job in hand and Supervisor starts them again with the new code.

The scheduler puts a small heartbeat job on the queue every minute. Health shows the queue worker as failing when no worker has run that job for 5 minutes. This works with every queue driver (database, Redis and others), so a stopped worker is noticed even when no orders are waiting.

On shared hosting without long-running processes, add a second cron job that starts the worker every minute and stops it before the next one:

* * * * * cd /home/USER/biteway-backend && php artisan queue:work --queue=dispatch,notifications,payments,default --stop-when-empty --max-time=55 >> /dev/null 2>&1

Redis for cache, queue and sessions

Optional, for a VPS. Biteway keeps its cache, queue and sessions in the database, which works on any hosting. On a VPS with many orders, Redis makes them faster. Biteway uses Laravel's built-in Redis support, so you don't need to install another package.

  1. Install Redis and the PHP extension phpredis (Ubuntu shown; match your PHP version):
sudo apt install redis-server php8.4-redis
sudo systemctl enable --now redis-server
  1. Set these lines in .env:
REDIS_CLIENT=phpredis
REDIS_HOST=127.0.0.1
REDIS_PORT=6379
REDIS_PASSWORD=null        # set one if Redis is reachable from other machines

CACHE_STORE=redis
QUEUE_CONNECTION=redis
SESSION_DRIVER=redis

You can switch one at a time; for example, only CACHE_STORE=redis.

  1. Apply the change:
php artisan optimize
php artisan queue:restart
  • When the queue moves to Redis, jobs still waiting in the database queue stay there. Switch when the queue is empty (Health shows "No jobs waiting"), or keep a database worker running until it is.
  • Moving sessions to Redis signs everyone out of the admin panel and the website once. The apps stay signed in.
  • Health pings Redis whenever the cache, the queue or sessions use it, and fails the check when Redis does not answer.

Horizon (optional)

Laravel Horizon is a dashboard for Redis queues. Biteway doesn't ship it and doesn't need it. If you want it on a VPS with Redis:

composer require laravel/horizon
php artisan horizon:install

Then replace the queue:work command in the Supervisor program with command=php /var/www/biteway-backend/artisan horizon, and set Horizon's queues to dispatch,notifications,payments,default (in this order) in config/horizon.php. Protect /horizon as the Horizon documentation describes. After every Biteway update, run composer require laravel/horizon again: the update installs the PHP packages of the new version, which do not include Horizon. Horizon is yours to maintain: Biteway support covers the queue worker described above.

Live updates on a VPS

Out of the box the apps and the website ask the server for changes every few seconds (polling). That works on any hosting. For instant updates, choose one of:

  • Firebase (no server of your own): see Mobile apps, then Integrations → Live updates → Firebase Realtime Database.
  • A Pusher-compatible server: Pusher Channels (hosted), or your own Laravel Reverb or Soketi on a VPS. Biteway talks to all three the same way and needs no extra package for it.

With a Pusher-compatible server, the server still stores every change, so polling keeps working: an app or browser whose connection drops polls until it is back, and if the server cannot be reached, Biteway keeps the changes in the database only and tries the server again 30 seconds later. The keys go in .env only; the admin panel shows whether they are set.

After setting the keys (see below for each server):

  1. Run php artisan optimize.
  2. Open Integrations → Live updates, choose Pusher-compatible (Pusher, Soketi, Reverb) and save.
  3. Click Test connection on the Pusher-compatible server card (the button appears once the keys are in .env). Health then shows Live updates: pusher, server reachable.

Pusher Channels (hosted)

Create a Channels app at Pusher and copy its keys into .env. Leave PUSHER_HOST empty: Biteway then uses Pusher's servers for your cluster.

PUSHER_APP_ID=1234567
PUSHER_APP_KEY=your-key
PUSHER_APP_SECRET=your-secret
PUSHER_APP_CLUSTER=us2

In the Pusher dashboard, keep client events off. Pusher limits one message to 10 KB; bigger changes are sent as "something changed" and the apps read the change from the server.

Laravel Reverb (your own server)

Reverb is a PHP WebSocket server. Install it in the backend folder:

composer require laravel/reverb

Add its keys to .env. Choose your own id, key and secret (long random strings), and use the same values for the PUSHER_ lines:

REVERB_APP_ID=biteway
REVERB_APP_KEY=your-random-key
REVERB_APP_SECRET=your-random-secret
REVERB_HOST=ws.your-domain.com
REVERB_PORT=443
REVERB_SCHEME=https
REVERB_SERVER_HOST=127.0.0.1
REVERB_SERVER_PORT=8080

# Biteway sends to Reverb on this server; the apps and browsers connect through Nginx.
PUSHER_APP_ID=biteway
PUSHER_APP_KEY=your-random-key
PUSHER_APP_SECRET=your-random-secret
PUSHER_HOST=127.0.0.1
PUSHER_PORT=8080
PUSHER_SCHEME=http
PUSHER_CLIENT_HOST=ws.your-domain.com
PUSHER_CLIENT_PORT=443
PUSHER_CLIENT_SCHEME=https

Keep Reverb running with its own Supervisor program (see Cron job and queue worker). Create /etc/supervisor/conf.d/biteway-reverb.conf:

[program:biteway-reverb]
command=php /var/www/biteway-backend/artisan reverb:start --host=127.0.0.1 --port=8080
user=www-data
numprocs=1
autostart=true
autorestart=true
stopwaitsecs=10
redirect_stderr=true
stdout_logfile=/var/www/biteway-backend/storage/logs/reverb.log
minfds=10000

Then run sudo supervisorctl reread && sudo supervisorctl update. After changing .env, run sudo supervisorctl restart biteway-reverb.

After every Biteway update, run composer require laravel/reverb again and restart Reverb: the update installs the PHP packages of the new version, which do not include Reverb.

Soketi (your own server)

Soketi is a Node.js WebSocket server (Node 18 or newer). Install it:

npm install -g @soketi/soketi

Run it with your own keys as a Supervisor program, /etc/supervisor/conf.d/biteway-soketi.conf:

[program:biteway-soketi]
command=soketi start
environment=SOKETI_DEFAULT_APP_ID="biteway",SOKETI_DEFAULT_APP_KEY="your-random-key",SOKETI_DEFAULT_APP_SECRET="your-random-secret",SOKETI_HOST="127.0.0.1",SOKETI_PORT="6001"
user=www-data
autostart=true
autorestart=true
redirect_stderr=true
stdout_logfile=/var/www/biteway-backend/storage/logs/soketi.log

Then run sudo supervisorctl reread && sudo supervisorctl update. In .env, use the same id, key and secret, with PUSHER_HOST=127.0.0.1, PUSHER_PORT=6001, PUSHER_SCHEME=http and the PUSHER_CLIENT_ lines as for Reverb.

Nginx in front of Reverb or Soketi

Give the socket server its own address (for example ws.your-domain.com) with an HTTPS certificate, and pass WebSocket connections on to it:

server {
    listen 443 ssl;
    http2 on;
    server_name ws.your-domain.com;

    ssl_certificate     /etc/letsencrypt/live/ws.your-domain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/ws.your-domain.com/privkey.pem;

    location / {
        proxy_http_version 1.1;
        proxy_set_header Host $http_host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "Upgrade";
        proxy_read_timeout 120s;
        proxy_pass http://127.0.0.1:8080; # 6001 for Soketi
    }
}

Behind Cloudflare, keep WebSockets switched on (Network settings). Only Nginx needs to reach port 8080 (or 6001), so keep that port closed in the firewall.

If it does not work: Test connection says whether the keys are refused (the PUSHER_ values differ from the server's) or the server cannot be reached (it is not running, or PUSHER_HOST or PUSHER_PORT is wrong). The apps and the website keep working by polling in the meantime.

Search with Meilisearch

Optional, for a VPS. By default, restaurant and dish search uses the database: MySQL full-text search, or simple matching on any database. Meilisearch finds names that are misspelled and finds names in every language you added (Bangla, Arabic and others). Biteway talks to Meilisearch directly, without another package. When Meilisearch is down, the database answers searches, so search keeps working.

  1. Install Meilisearch on the server (see its documentation), and run it with a master key, for example as a Supervisor program or a systemd service:
meilisearch --master-key="a-long-random-key" --env=production --db-path=/var/lib/meilisearch
  1. Set these lines in .env. The key is a server secret and never goes to the apps:
MEILISEARCH_HOST=http://127.0.0.1:7700
MEILISEARCH_KEY=a-long-random-key
MEILISEARCH_INDEX_PREFIX=biteway_   # change it when several sites share one Meilisearch
MEILISEARCH_TIMEOUT=2               # seconds a search waits before the database answers instead

Then run php artisan optimize.

  1. Open Integrations → Search, choose Meilisearch (VPS) and save. The status line tells you whether Meilisearch answers.
  2. Click Reindex now (it appears once Meilisearch is chosen and MEILISEARCH_HOST is set). The queue worker sends every restaurant and dish to Meilisearch. On the command line, run:
php artisan biteway:search:reindex                      # every index
php artisan biteway:search:reindex --model=menu_items   # only dishes (or restaurants)

After that, the queue worker sends each new or changed restaurant and dish automatically. Changes to stock or prices are not sent, because search doesn't need them. Health compares the number of documents in each index with the database and warns when they differ by more than a few. To fix it, run the reindex again.

To go back to database search, choose MySQL full-text or Simple matching under Integrations → Search. Nothing else is needed.

Files on S3 or a CDN

Biteway keeps uploads on the server's own disk by default (storage/app/public for pictures and reels, storage/app/private for documents). On a VPS you can keep them in an S3-compatible bucket instead, and serve public files through a CDN. The S3 driver is included; you only change .env.

There are two sets of files:

Set What .env setting Choices
Public files Logos, covers, menu photos, promotion banners, reels, chat pictures, the pictures uploaded in Settings BITEWAY_UPLOAD_DISK public (this server) or s3
Private documents Restaurant and rider documents, delivery proof photos, problem report photos, safety report photos, data exports BITEWAY_PRIVATE_UPLOAD_DISK local (this server) or s3_private

Private documents are only ever opened through short-lived signed links, so they need a second bucket that is never public. Never put them in the public bucket.

1. Create the buckets and a key

Create two buckets (for example biteway-files and biteway-private) and an access key that can read, write and delete in both. Then make the public bucket readable by everyone:

  • AWS S3: keep "Block public access" on for the private bucket. For the public bucket, turn off "Block public access" and add a bucket policy that allows s3:GetObject on arn:aws:s3:::biteway-files/*. Leave AWS_VISIBILITY=private (buckets with ACLs disabled, the AWS default, refuse public-read ACLs). Only if your bucket has ACLs enabled can you use AWS_VISIBILITY=public instead of a policy.
  • Cloudflare R2: turn on public access for the public bucket (an r2.dev address or your own domain) and put that address in AWS_URL.
  • Wasabi: add a bucket policy allowing public s3:GetObject on the public bucket.
  • MinIO: run mc anonymous set download myminio/biteway-files.

The keys stay in .env only; the installer and the admin panel never ask for them.

3. Copy the files already uploaded

Changing the disk in .env does not move existing files. Copy them first, while the site still uses the old disk:

php artisan biteway:storage:move public s3 --dry-run          # counts the files and their size, copies nothing
php artisan biteway:storage:move public s3                    # copies the public files
php artisan biteway:storage:move local s3_private --private   # copies the private documents
  • The command copies every file the app refers to (database columns, image records and thumbnails, the pictures in Settings, the share picture and the homepage picture). Files nothing refers to are left behind.
  • The files on the old disk are never deleted. Delete them yourself once the site works from the bucket.
  • You can run it again at any time: files already in the bucket with the same size are skipped, so an interrupted copy just continues. Add -v to see every file.
  • Files a record names but the old disk does not have are listed as missing. They were already gone; the copy carries on.

When it says Done, set the line it prints (for example BITEWAY_UPLOAD_DISK=s3 and BITEWAY_PRIVATE_UPLOAD_DISK=s3_private) in .env and run php artisan optimize. Then open Health: Uploads storage and Private files storage write, read and delete a test file in each bucket.

CORS

Pictures and videos shown with <img> and <video> need no CORS. Add a CORS rule allowing GET from your site's address (and the Customer Website's) only if a browser page reads the files with JavaScript; R2 and MinIO have no rule until you add one.

A CDN for public files

Set the CDN's address and Biteway uses it for every public file address. Private documents keep their signed links.

BITEWAY_CDN_URL=https://cdn.your-domain.com

The CDN address replaces the scheme and host of a file's address and keeps the path:

  • Local disk behind a pull CDN (works on shared hosting too): point the CDN's origin at your site. https://api.your-domain.com/storage/menus/4/burger.jpg becomes https://cdn.your-domain.com/storage/menus/4/burger.jpg.
  • Bucket behind a CDN (CloudFront, Cloudflare): point the CDN's origin at the bucket. https://biteway-files.s3.amazonaws.com/menus/4/burger.jpg becomes https://cdn.your-domain.com/menus/4/burger.jpg. With MinIO or another path-style address, the bucket name stays in the path, so point the CDN at the endpoint.

Run php artisan optimize after the change. Health → CDN for files puts a test file on the uploads disk and fetches it through the CDN; it must come back.

Converting reel videos

Restaurants upload reels as MP4 or WebM, and by default Biteway keeps the file as uploaded. On a server with ffmpeg, Biteway can convert every new reel into a 720p H.264 MP4 that starts playing before it has fully downloaded. The files are smaller and play the same on every phone.

Install ffmpeg

sudo apt install ffmpeg        # Ubuntu and Debian
sudo dnf install ffmpeg        # Fedora, Rocky and AlmaLinux (with RPM Fusion)

Biteway finds ffmpeg and ffprobe on the server's PATH. If they live elsewhere, set their paths in .env:

FFMPEG_PATH=/usr/local/bin/ffmpeg
FFPROBE_PATH=/usr/local/bin/ffprobe
BITEWAY_REELS_CONVERT_TIMEOUT=900   # seconds one conversion may take

Shared hosting rarely has ffmpeg. Reels still work there, as uploaded.

Switch it on

Go to Settings → Food reels and turn on Convert videos (needs ffmpeg). The switch is greyed out, with a note, while the server has no ffmpeg.

  • A new reel shows Processing while its video is converted, then moves on as usual: Pending for review, or straight to the app when Publish now was ticked. It can't be published or rejected while it is processing.
  • Conversion runs on the queue worker (see Cron job and queue worker), so keep the worker running. A reel converts in seconds to a few minutes, depending on its length and the server's processor.
  • If ffmpeg fails or is missing, the reel keeps its uploaded file and moves on; the error is written to the log (storage/logs).
  • With the files on S3, the video is downloaded to a temporary file, converted and uploaded again.
  • Conversion is heavy work for the processor. On a small server, keep reels short (Longest video (seconds) in the same settings).

Health → Video conversion shows Off, ffmpeg found, or a warning when conversion is on without ffmpeg.

Going live

Before opening your platform to the public, check:

Updating

Biteway updates itself from the new version's zip, with a backup and a way back. The Updates page in the admin panel (Super Admin) shows the same steps.

  1. Upload the new Biteway zip from CodeCanyon to the server, for example next to the biteway-backend folder.
  2. See what it will change. Nothing is changed yet:
cd /var/www/biteway-backend
php artisan biteway:update /path/to/biteway.zip --check
  1. Apply it. The site shows a maintenance page for about a minute:
php artisan biteway:update /path/to/biteway.zip

The update backs up the database and the files it replaces first (in storage/app/updates/backups, readable only by the site's own user; the newest three are kept), then copies the new files, runs the database migrations and clears the caches. Your .env, uploads, storage, installed add-ons and built assets are never changed. If a step fails, everything is put back. The update's backup only undoes that update; keep your own backups as well (Backups and restore).

  • When the new version changes the PHP packages, the update runs composer install itself, so Composer must be available on the server. Without Composer, it stops before changing anything and tells you so.
  • When it changes the admin panel's styles or scripts, --check says so: run npm ci && npm run build after the update. Until you do, new admin features that need those files stay hidden (for example the route map on an order page), and the panel can look out of date.
  • Run php artisan optimize again afterwards, because the update clears the caches.

To undo a finished update, run php artisan biteway:update:rollback, or use Roll back on the Updates page. Orders and payments recorded after the update would be lost, so the page tells you how many first.

Both commands ask you to confirm before they change anything; answer yes. Run without questions (-n, for example from a script), the update goes ahead but the rollback does nothing and exits with an error, so always run a rollback by hand.

  • Only the latest applied update can be rolled back. To undo an older one, roll back the newer ones first, newest first; --force does not get around this.
  • Updates and rollbacks run one at a time. While one is running, another is refused with "Another update or rollback is running": wait for it to finish, then try again. The lock is kept in storage/app/updates, so that folder must be writable.
  • If another update finished after you checked one, run the update again so it is checked against the version now installed.
  • "Failed, not put back" (or "Interrupted") on the Updates page means an update failed or stopped and its files and database were not restored, so the site may be partly on the new version. Its backup is kept, and older updates can't be rolled back until it is fixed. Restore the site and database from your own backup, then contact support.

💾 Backups and restore

How to back up your platform, keep the backups safe and bring the site back from one. Set this up before you go live, and test a restore before you need one.

What to back up

What Where Why
The database MySQL, MariaDB or SQLite Orders, payments, customers, restaurants, menus, settings and the ledger.
.env biteway-backend/.env The database details, your mail settings and the APP_KEY.
Uploaded files storage/app/public Photos, logos, menu images, reels and documents.
Private files storage/app/private Rider documents, data exports and the Firebase key uploaded in the admin panel.
Add-ons addons/ and public/addons/ The installed add-ons, such as the Customer Website and the Restaurant Portal.
The Firebase key file The file FIREBASE_CREDENTIALS in .env points at Only if you placed the key on the server yourself instead of uploading it under Firebase.

Keep a copy of the APP_KEY from .env in a safe place, apart from the backups. Biteway encrypts the saved secrets (payment gateway keys, provider keys, the uploaded Firebase key) and the payout details of restaurants and riders with it. Without the same APP_KEY, a restored site can't read them: you would have to enter every key again, and restaurants and riders would have to add their payout accounts again.

A backup holds your customers' personal data. Store it where only you can reach it.

What not to back up

These are rebuilt from the Biteway zip, so leave them out:

  • vendor/ (rebuilt with composer install)
  • node_modules/ (rebuilt with npm ci)
  • public/build/ (rebuilt with npm run build)
  • storage/logs/, storage/framework/ and bootstrap/cache/

Keep the Biteway zip of the version you run, so you can rebuild these on a new server.

Files on Amazon S3 or another cloud disk are not downloaded into a backup. Use the provider's own backups instead: on S3, turn on versioning for the bucket, so a deleted or overwritten file can be brought back. The local storage/app/public and storage/app/private folders are still backed up, because storage/app/private holds the Firebase key uploaded in the admin panel.

Three ways to back up

Choose one. Whichever you choose, copy the backups off the server.

1. Your hosting panel

Most hosts (cPanel, Plesk and VPS providers) offer daily backups or server snapshots. Turn them on, and check that they include both the database and the files of biteway-backend. A snapshot of the whole server is the simplest way back, but it is often kept by the same provider as the server itself, so keep your own copy too.

2. The backup command

Biteway backs itself up into one zip file:

cd /var/www/biteway-backend
php artisan biteway:backup

The zip holds:

  • the database (MySQL, MariaDB or SQLite; no mysqldump needed, so it also works on shared hosting),
  • storage/app/public and storage/app/private, always, even when uploads are on S3,
  • addons/ and public/addons/,
  • the Firebase key file, if FIREBASE_CREDENTIALS points at one, even when the file is outside biteway-backend,
  • a list of every file with its checksum, used to check the zip before a restore.

Earlier backups (storage/app/backups) and the updater's backups (storage/app/updates) are never put in the zip. When uploads are on S3 or another cloud disk, only the files in the bucket are left out: the command says so, and the zip's list notes which disks were left out. Symbolic links, such as the links an add-on makes to its files, are saved as links, not as copies of the files they point at.

Each zip is named after the time it was made, in UTC, for example biteway-backup-20261116-023000-k3x9.zip. Backups go to storage/app/backups. After each backup, the newest ones are kept in that folder and older ones are deleted: how many is the Backups to keep setting (7 unless you change it, from 1 to 90). The command also deletes the updater's backups that can no longer be used to roll back an update.

Option What it does
--to=/path/to/folder Saves the zip in another folder, for example a mounted backup drive. The older backups deleted are the ones in that folder.
--keep=14 Keeps the newest 14 backups in that folder, instead of the Backups to keep setting.
--no-files Backs up the database only.
--with-env Adds .env to the zip.

To keep the backups in another folder every time, set BITEWAY_BACKUP_PATH in .env, for example BITEWAY_BACKUP_PATH=/var/backups/biteway, then run php artisan optimize. The daily backup and Health use this folder. A folder inside public/ is refused, because anyone could download the backups from it, and so is a folder inside one that is backed up (such as storage/app/public or addons/), because a restore replaces it.

Run the command as the web server user (for example sudo -u www-data php artisan biteway:backup), so the backup folder stays writable for the daily backup. Only one backup or restore runs at a time; another one is refused with "Another backup or restore is running". Files changed while a backup runs may be caught half way, so back up at a quiet hour and not while you upload files or install an add-on.

.env is left out unless you add --with-env, because it holds the APP_KEY. Keep .env (or at least the APP_KEY) in a password manager or another safe place. If you use --with-env, anyone with the zip can read your saved secrets, so store it as carefully as the key itself.

Daily backup. To back up automatically, open Settings → General in the admin panel and, under Backups, turn on Back up every day. It is off by default. Backup time (2:00 AM unless you change it) is read in the platform time zone under Settings → Localization & currency; Backups to keep sets how many backups stay in the folder. The daily backup holds the same as the command without options, so not .env. It runs from the cron job, so the cron job must be running (Deployment).

Health in the admin panel warns when the newest backup is older than 48 hours, or when there is none yet, and shows an error when the backup folder can't be written. It only looks at the default folder (storage/app/backups, or BITEWAY_BACKUP_PATH): backups saved elsewhere with --to don't count.

On shared hosting, run the command from the host's terminal, or add it under Cron Jobs with the full path to PHP, for example once a night at 2:30 AM:

30 2 * * * cd /home/USER/biteway-backend && /usr/local/bin/php artisan biteway:backup >> /dev/null 2>&1

3. Your own cron job (VPS)

If you prefer the standard tools, a nightly script with mysqldump and tar works as well. Save it as /usr/local/bin/biteway-backup.sh:

#!/bin/sh
set -e
APP=/var/www/biteway-backend
DEST=/var/backups/biteway
DAY=$(date +%Y-%m-%d)

mkdir -p "$DEST"
mysqldump --defaults-extra-file=/root/.biteway-db.cnf --single-transaction --quick --routines biteway \
    | gzip > "$DEST/database-$DAY.sql.gz"
tar -czf "$DEST/files-$DAY.tar.gz" -C "$APP" \
    --exclude=storage/app/backups --exclude=storage/app/updates \
    .env storage/app addons public/addons

# Keep 7 days.
find "$DEST" -name '*.gz' -mtime +6 -delete

Put the database user and password in /root/.biteway-db.cnf, so they don't show in the process list, and run chmod 600 /root/.biteway-db.cnf:

[client]
user=biteway
password=your-database-password

Change biteway after --routines to your database name. If FIREBASE_CREDENTIALS points at a file outside biteway-backend, add that file to the tar line. Then make the script executable and run it every night at 2:30 AM (sudo crontab -e):

sudo chmod 700 /usr/local/bin/biteway-backup.sh

30 2 * * * /usr/local/bin/biteway-backup.sh >> /var/log/biteway-backup.log 2>&1

--single-transaction takes a consistent copy without locking the tables, so the site keeps taking orders while it runs.

The updater's backup is not a general backup

biteway:update backs up the database and the files it replaces, so an update can be rolled back. It is only meant for undoing that update shortly after it ran: it does not hold your uploads, your add-ons or .env. These backups are deleted after each update and each biteway:backup once the time to roll back has passed; the latest applied update's backup is kept. Keep your own backups as well.

How much space backups need

Each backup is a full copy of the database and every uploaded file on the server: photos, documents and food reel videos. The folder needs about the number of backups you keep × the size of one backup: with 5 GB of uploads and 7 backups kept, plan for about 35 GB.

  • biteway:backup refuses to start when the disk doesn't have room for another backup plus 1 GB to spare, so a backup never fills the disk. Free some space, keep fewer backups, or save them elsewhere with --to.
  • Health shows how many backups are kept and how much space they use, and warns when the disk is nearly full.
  • Files stored on S3 or another cloud disk are not in the zip, so backups stay small.
  • Keep only a few backups on the server and the rest elsewhere (next section).

Copy backups off the server

A backup on the same server is lost with the server. Copy every backup to another place: another server, cloud storage or your computer.

With rsync, to another server over SSH (add it to the cron job after the backup):

rsync -a /var/www/biteway-backend/storage/app/backups/ backup@backup.example.com:/backups/biteway/

With rclone, to cloud storage such as Amazon S3, Backblaze B2 or Google Drive (set up the remote once with rclone config):

rclone copy /var/www/biteway-backend/storage/app/backups remote:biteway-backups

By hand, download the newest zip from storage/app/backups with your hosting panel's file manager or an SFTP app.

If you set BITEWAY_BACKUP_PATH, copy that folder instead. With the cron-job way, copy /var/backups/biteway.

Restore

Restore onto the same Biteway version, or a newer one, with the same type of database. Restoring replaces the current database and files, so first make a fresh backup of the current state if it still works.

With the backup command

  1. Upload the backup zip to the server, for example to /var/www/backups/. Keep it out of the folders the restore replaces (storage/app/public, storage/app/private, addons/ and public/addons/): a zip inside one of them is refused.
  2. Restore it, as the web server user, so the restored files belong to it:
cd /var/www/biteway-backend
sudo -u www-data php artisan biteway:backup:restore /var/www/backups/biteway-backup-20261116-023000-k3x9.zip

First, the command checks the zip without changing anything. It stops if:

  • the zip is not a Biteway backup, or holds a file a Biteway backup doesn't have,
  • a file in the zip doesn't match its checksum (the zip is damaged or was changed),
  • the backup was made by a newer Biteway version than the one installed ("Update to 1.2.0 or newer first"),
  • the backup holds another type of database. MySQL and MariaDB count as the same type; a SQLite backup can't be restored into MySQL or MariaDB, or the other way round,
  • the site is in demo mode.

It then shows what the backup holds and asks you to confirm; --force skips the question and does nothing else. Then it:

  1. shows the maintenance page,
  2. takes a copy of the current database,
  3. imports the backup's database,
  4. replaces each backed-up folder with the backup's copy. Files added since the backup are removed from those folders,
  5. runs storage:link, migrate --force, optimize:clear and queue:restart,
  6. brings the site back.

Symbolic links, such as an add-on's links to its files, are made again. If one can't be, the command says so: switch that add-on off and on again under Add-ons.

If the import or replacing a folder fails, the database and the folders are put back as they were and the site stays on the maintenance page, with the reason. If putting them back fails too, the command prints where the copies from before the restore are kept. If a step after the folders were replaced fails (for example a migration), the command says the backup was restored but finishing it failed, and the site also stays on the maintenance page. Fix the cause, then run php artisan up.

.env is never overwritten. When the backup holds .env (made with --with-env), it is saved beside yours as .env.from-backup, and the command warns when its APP_KEY differs from yours. Compare the two files and copy what you need into .env, then delete .env.from-backup.

The restore unpacks the zip under storage/app first, so leave free disk space of at least the backup's size. When it finishes, run php artisan optimize, because the restore clears the caches.

On a new server, set up Biteway first and then restore:

  1. Upload the Biteway zip of the same version (or newer) and point the domain at public, as in Installation.
  2. Run composer install --no-dev --optimize-autoloader and npm ci && npm run build.
  3. Put your .env back, with the same APP_KEY. Change the database details if the database is new, and create that database (empty).
  4. Run php artisan biteway:backup:restore with your zip, as above. Use the same type of database as the old server: a MySQL backup can go into MariaDB, but not into SQLite.
  5. Set up the cron job and the queue worker again (Deployment).

From your own cron-job backup

Run these in order, in /var/www/biteway-backend:

  1. Show the maintenance page:
php artisan down
  1. Import the database (this replaces its contents):
gunzip < /var/backups/biteway/database-2026-11-16.sql.gz | mysql --defaults-extra-file=/root/.biteway-db.cnf biteway
  1. Put back .env, storage/app and the add-ons:
tar -xzf /var/backups/biteway/files-2026-11-16.tar.gz -C /var/www/biteway-backend
sudo chown -R www-data:www-data storage bootstrap/cache
  1. Rebuild what is not in the backup, and bring the database up to the installed version:
php artisan storage:link
composer install --no-dev --optimize-autoloader
npm ci && npm run build
php artisan migrate --force
php artisan optimize
  1. Restart the queue worker, so it uses the restored code and settings:
php artisan queue:restart
  1. Bring the site back:
php artisan up

Test a restore

A backup you have never restored may not work. Every three months, and after a big change to your server, restore the newest backup into a staging copy: a separate folder (for example /var/www/biteway-staging), its own database and its own address (for example staging.example.com). Never test on the live database.

  1. Set up the staging folder as in On a new server, with a copy of your .env that keeps the same APP_KEY but uses the staging database, APP_URL=https://staging.example.com and MAIL_MAILER=log, so no email reaches your customers.
  2. Restore the newest backup into it, as described above. Then switch its payment gateways to test mode under Payments.
  3. Check:
    • Health shows no errors other than the cron job, the queue worker and the backup age, which staging does not need.
    • A recent order opens under Orders, with its timeline and payments.
    • Uploaded images show, for example a restaurant's logo and its menu photos.
    • Payouts shows where a restaurant's or rider's money is sent (the masked account details). This proves the APP_KEY is right.
  4. Delete the staging copy and its database when you are done.

Don't start a queue worker or cron job for staging, so it never charges, pays out or notifies real people. Repeat the test every three months.

Setup assistant

Super Admin → Setup assistant (also linked from the dashboard's go-live checklist) walks you through the setup in nine steps. Each step shows whether it is Done, Needs attention or Optional, what is missing, a link to the page where you fix it and, where the service can be checked live, a Test button that shows exactly what the provider answered. The statuses come from the same checks as the go-live checklist and Health, so the three always agree.

  1. Branding & support contact: your platform name, logo and the support email and phone (the shipped support@example.com must be replaced).
  2. Currency & region: the currency (choose it before the first order), phone country, timezone and distance unit, and the amounts with no starting value for your currency (rider pay, the riders' cash limit, what a restaurant may owe).
  3. Maps: map tiles need no key. With Google Maps, Test looks up a fixed address with your browser key, for example Google answered: REQUEST_DENIED — this key isn't enabled for the Geocoding API. A key limited to your website's address can't be fully checked from the server, so also open a page with a map on your website. The Android and iOS keys are inside the app builds and can't be checked here.
  4. Sign-in codes (SMS / Firebase): type a phone number with its country code and Test sends it a text through Twilio or BulkSMSBD, showing the provider's reason if it refuses. With Firebase Phone Authentication, test by signing in to the customer app.
  5. Push notifications: type the phone number of an account in any of the apps (customer, rider or restaurant staff), with its country code, such as +15125550100, and click Test. The push goes to that account's most recently used device with notifications allowed, and the result names the account type and the device. The field starts with the phone saved on your admin profile, if there is one. It tells you if no account uses the number, if the number is not valid, or if the account has no device with notifications allowed (it then checks the Firebase key). The Activity Log keeps only the number's last four digits.
  6. Payments: pick a switched-on gateway and Test asks it whether it accepts your keys (Stripe reads your balance, PayPal and bKash ask for a token, SSLCOMMERZ looks up a made-up transaction). Nothing is charged.
  7. Email: Test sends an email to your admin address, or tells you the server only writes emails to the log.
  8. Live updates (optional): polling needs nothing; with a Pusher-compatible server Test checks its keys.
  9. Go live checklist: debug mode off, HTTPS, uploaded pictures showing, and anything an add-on asks for; then open Health to see the queue worker and the cron job running.

Each test is written to the Activity Log, and at most five tests run per minute. The setup assistant has no on/off switch: it is a helper page for the Super Admin, not something customers see. On the live demo the steps are shown but the tests are switched off.

First-time setup

Work through these steps once, in this order. Every setting has a short explanation under it in the panel.

1. Your brand

Settings → General:

  • App names: the platform name, and the names of the customer, rider and restaurant apps. The name under each app's icon on the phone is set when the app is built (Mobile apps).
  • Logo & colors: the logo, favicon, and the primary and secondary colors. The apps use these colors. The customer app's header and main buttons use the Secondary color, so to rebrand, change both Primary and Secondary (Colors).

  • Tax invoices: your company name, address, tax ID and country (two letters), and the invoice number prefix.
  • Backups: Back up every day (off by default), the Backup time in the platform time zone, and how many Backups to keep. It needs the cron job (Backups and restore).

The apps fetch these settings each time they start and each time they come back to the screen after 5 minutes or more, and apply new colors and texts without restarting; new pictures and the logo show at the latest when the app next starts. A change reaches an open app the next time it is reopened or brought back after 5 minutes or more, and a closed app when it next starts.

2. Currency, phone country and time

Settings → Localization & currency: the currency symbol and its position, decimal places, the default phone country for sign-in, the Distance unit (kilometers or miles), and the platform time zone. The apps, the website and the admin panel show distances in that unit. The currency itself was chosen in the installer.

3. Where you deliver

Zones has three tabs, used in this order:

  1. Countries: each with its dialling code and currency.
  2. Cities: each in a country, with its time zone and the point where its maps open. Opening hours of restaurants follow their city's time zone.
  3. Zones: delivery areas drawn on a map. Click Add zone, click the map to add points, and drag a point to move it. Customers outside every active zone are told that delivery is not available.

4. Prices and your income

Under Pricing:

  • Delivery fees: what delivery costs in each zone: a base fee, a price per kilometer, a minimum and maximum, and an order value above which delivery is free. Prices are always entered per kilometer, even when the distance unit is Miles; the form then shows a note (1 mi = 1.61 km).
  • Surge: periods when a zone's delivery fee is multiplied, for example at busy hours.
  • Taxes: per country, or per zone where it differs.
  • Plans: the plans restaurants are on: a commission, a monthly fee, or both.
  • Commission: exceptions for a menu category, a restaurant, a zone or an order type. The most specific rule wins; otherwise the restaurant's plan applies.

Settings → Ordering holds the rest of the order rules: the service fee, fraud rules, late-order limits, order types (pickup, dine-in), scheduled orders, time limits for paying, rating and reporting a problem, reusable containers, calling the rider, the wallet top-up limits, payouts and how much a restaurant may owe, delivery distances and order chat. Food freshness

Warn when ready food waits for pickup checks every minute for deliveries with a platform rider whose food the kitchen has marked ready but the rider hasn't picked up yet. Three times, counted from the moment the order is ready, set what happens:

Setting Default What happens
Push the rider and the restaurant after (minutes ready) 8 The assigned rider and the restaurant's staff get one push each, and both apps mark the order as waiting.
Email dispatch admins and list it on the flight deck after (minutes ready) 15 Admins who can assign riders get one email, the order is listed under Food waiting for pickup on the flight deck, and both apps mark it late.
Give the delivery to another rider after (minutes ready) 20 If the assigned rider still hasn't reached the restaurant and another rider nearby can take it, the delivery is offered to that rider through the usual dispatch, and the first rider is told "The food waited too long for pickup, so the delivery went to another rider." With nobody else free, the first rider keeps it, and it is checked again each minute. The first rider is offered it again only if no other rider takes it. 0 never does this.
  • Riders see "Food ready N min ago" on the delivery, amber once it passes the first time and red once it is late.
  • Restaurants see the waiting time on ready tickets on the kitchen board, with Food waiting or Waiting too long at the same times. Pickup orders waiting for the customer get the timer too, but no push or email.
  • The messages are listed under Content → Notifications as Food waiting for pickup (riders), Ready order waiting for its rider (restaurant teams) and Ready food waiting too long (admins), where you can reword them or switch a channel off. Each one is sent once per order.

Group Meal Cart

Let customers order together from one shared cart lets a group of friends or colleagues fill one cart at one restaurant branch, each adding their own dishes, and send it to the kitchen as one order.

  1. Start: a signed-in customer opens a restaurant and starts a group cart. They are its host, and they can have one open group cart at a time.
  2. Share the link: the host shares the invite link, https://your-site/g/…. On a phone with the customer app it opens the app's join screen; otherwise it opens the Customer Website (with the Customer Website add-on).
  3. Join: whoever opens the link signs in and joins under their name. Only signed-in customers can join, up to the member limit below.
  4. Add their own items: each member adds, changes and removes only their own dishes, with the same sizes, options and split-pizza halves as a normal cart. Everyone sees the whole cart, sorted by person, as it changes.
  5. Done: each member marks themselves done adding. The host then picks the order type, address and time, as at checkout, and locks the cart. Until someone has paid, the host can unlock it to let people keep adding.

When locking, the host picks one of two ways to pay:

Way to pay How it works
Host pays for everyone The host pays the whole order at once when placing it. This is the only way the order can be paid in cash.
Everyone pays their own Each member pays their share online, through the same payment gateways as checkout, within the time set below. The host then places the order. At the deadline, the host covers anyone who hasn't paid, online, and can also choose to cover them sooner.

How fees are shared: the host and every member with at least one dish pay; a member with no dishes pays nothing. Each pays their own dishes (after the restaurant's offers) and container deposits, plus an even part of the packaging, delivery and service fees, the tip and any donation; added tax is shared in proportion to each person's dishes. Uneven cents go to the host, so the shares always add up to the order total. The host's promo code and invite discount come off the host's share, and nobody's share goes below zero.

The locked price holds: when everyone pays their own, the prices, fees and promo code worked out when the host locks the cart stay valid until 5 minutes after the members' time to pay ends, so placing the order in time never changes the price. If the host places it later and the prices have changed meanwhile (an offer started or ended, a menu price or delivery fee was edited), the order is priced again and the shares are worked out again the same way:

  • A member who already paid more than their new share gets the difference back automatically, to the card they paid with.
  • A member who paid less than their new share owes nothing more: the host covers the difference.
  • The host pays whatever is left, so the payments always add up to the order total.

What members see: members other than the host see the area and city the order is delivered to, not the host's address, and see that a promo code is applied, not the code itself.

Refunds of a group order go back to each person who paid. If the order is cancelled or rejected, each member's share goes back to their own card and the host's payment to the host. When you refund a delivered group order from its order page, each member who paid a share gets their part, in proportion to what they paid, to their own card (if you refund to the card) or their own wallet (if you refund to the wallet); the host gets the rest. A member's money never goes to the host's wallet.

Safety timeline

Show each order's tamper-evident safety timeline adds a Safety timeline card to every order page in the admin panel. It lists everything that happened to the order, in order, with who did it, when, and the first characters of its seal:

  • status changes, with the reason when one was given
  • delivery and handover codes entered, right or wrong
  • the rider arriving at the restaurant and at the customer
  • the delivery photo taken at the door
  • problem reports, the restaurant's answer and your refund or rejection
  • refunds, chargebacks and how they were closed
  • rider SOS alerts and incident reports about the order, and how they were handled
  • escalations from the flight deck
  • food-freshness alerts (with Food freshness on)

The card has three buttons:

Button What it does
Verify Checks the whole timeline again and shows Verified: 23 events, chain intact, or the first event that doesn't check out and why (changed, removed, out of order, cut off at the end, or not sealed by your platform). It also checks that every record still holds what its event sealed (a status change's time and who made it, a refund's amount…) and that every note and reason still reads as it was written, and names the event whose record or text was changed.
Export PDF Downloads a printable timeline with the verification result, to send to a customer, a bank or an insurer.
Export JSON Downloads every event with its seals, so someone else can check the timeline without your admin panel (see below).
  • Always recorded. Every order's timeline is recorded whether this switch is on or off, so switching it on later shows complete timelines. The switch only shows the card and the portal page.
  • Tamper-evident. Each event is sealed with a SHA-256 hash that includes the hash of the event before it, and signed with a key made from your APP_KEY. The order also keeps its last event's number and hash, signed the same way, so events cut from the end, or a whole timeline deleted, are caught too. Changing, removing or reordering an event in the database, editing a record an event sealed, or replacing a delivery or problem photo on disk, shows up in Verify. A timeline that was tampered with is never sealed again: nothing more is added to it until you look into it. Photos are never copied into the timeline, only their SHA-256 fingerprint.
  • Written text is sealed as a fingerprint. Anything a person typed (the customer's problem note, the restaurant's answer, your refund, rejection and escalation notes, refund and chargeback reasons, a rider's safety-report description, the reason given for a status change such as a cancellation or a failed delivery) is sealed only as its SHA-256 fingerprint and length. The card reads the words from the report, reply or status change itself, and shows them while they still match the fingerprint. Types, amounts, statuses and codes (such as the problem category) are sealed as they are.
  • Erased at the customer's request. When a customer or rider deletes their account, what they wrote or sent on orders is erased (see Privacy requests), and each of those orders gets a Customer's text removed at their request (or Rider's) event, which names only the records, never the words. The timeline still verifies, the text shows as Removed at the customer's request and their photos as Photo removed at the customer's request. When you delete the account for them, the event reads Customer's text removed at an admin's request and the text Removed at an admin's request, and the event records which admin. Photos kept for an open chargeback or problem get their own event when the dispute closes and they are erased.
  • Text changed after it was recorded. If a note or reason is edited in the database, or blanked without an account deletion, the card shows Text changed after it was recorded in red in place of the words, and Verify reports that event. A problem or safety-report photo replaced or deleted on disk any other way shows Photo replaced or deleted after it was recorded, and Verify reports it too.
  • Who sees it: admins whose role can view orders. With the Restaurant Portal add-on, restaurants read their own orders' timeline in the portal, without the seals, Verify or exports, and without the customer's name, photo fingerprints, rider locations, safety-report details or your notes. Customers don't see it.
  • Older orders: the update notes the newest order when the timeline starts recording (the signed timeline.recorded_since setting). After updating, run php artisan biteway:timeline:backfill once to build the timelines of the orders placed before then. Events built this way are marked rebuilt from records, and code entries can't be rebuilt because they left no record. Running it again changes nothing. An older order that changes before you run it is rebuilt at that moment. A newer order is never rebuilt: its timeline was recorded as things happened, so one that is missing was removed, and Verify reports it.
  • Resealing: php artisan biteway:timeline:reseal seals timelines again in the current format. You only need it if support asks you to run it.
  • Keep your APP_KEY. If you ever change it, put the old one in APP_PREVIOUS_KEYS in .env, or older timelines no longer verify.

Checking a JSON export without the admin panel. Whoever checks it needs the timeline key, which php artisan biteway:timeline:key prints. It is not your APP_KEY, but anyone with it can also make seals, so give it only to the person checking. For each event, in sequence order:

  1. Take the event without hash, signature, texts and files (and without scheme when it is biteway.order-timeline.v1), written as JSON with the keys in alphabetical order at every level, no spaces, and slashes and non-English letters left as they are.
  2. Its SHA-256, in hex, must equal hash. previous_hash must equal the hash of the event before (64 zeros for the first event).
  3. HMAC-SHA256 of hash with the timeline key, in hex, must equal signature.
  4. head names the last event your platform signed: its sequence and hash must be the last event's, and its signature must equal HMAC-SHA256, with the timeline key, of the SHA-256 (hex) of {"hash":…,"order":…,"sequence":…,"type":"biteway.order-timeline.head"} (the last hash, the order's UUID and the last sequence, keys in that order, no spaces).

Written text appears in payload only as {"sha256": …, "chars": …}. Each event's texts lists those fingerprints with a status: verified (the stored text still matches, and text holds it, so its SHA-256 can be checked too), removed (erased at the person's request; no text) or changed (no longer matches; no text). Each event's files does the same for photos (verified, removed or changed), and files is left out of the body too. The export's how_to_check says the same.

The sample data switches it on, and every demo order has its timeline.

  2. In the admin panel, enter the apps' bundle IDs, separated by commas, under Integrations → Google and Apple sign-in → Apple client IDs, for example com.yourbrand.customer, com.yourbrand.rider.
  3. Switch on Settings → Sign-in → Sign in with Apple.

Release builds

Android: signing key

Google Play needs every upload signed with your own upload key. Create one once and keep it, and its passwords, safe: without it you cannot update your app.

keytool -genkey -v -keystore ~/upload-keystore.jks -keyalg RSA -keysize 2048 -validity 10000 -alias upload

Copy android/key.properties.example to android/key.properties and fill it in. storeFile is the full path to the file keytool made; write it out in full, because ~ is not expanded here:

storeFile=/absolute/path/to/upload-keystore.jks
storePassword=your-keystore-password
keyAlias=upload
keyPassword=your-key-password

Without key.properties, release builds are signed with the debug key: fine for testing, but Google Play rejects them. Never share or commit key.properties or the .jks file.

Then build the bundle to upload to Google Play:

flutter build appbundle --release --dart-define=API_BASE_URL=https://api.your-domain.com

The file is build/app/outputs/bundle/release/app-release.aab. For an APK to install directly on phones, use flutter build apk --release with the same --dart-define.

iOS

  1. Open ios/Runner.xcworkspace in Xcode, select the Runner target, and under Signing & Capabilities choose your Team (an Apple Developer account) and check the Bundle Identifier (Package name).
  2. Build the archive:
flutter build ipa --release --dart-define=API_BASE_URL=https://api.your-domain.com
  1. Upload build/ios/ipa/*.ipa with the Transporter app, or open build/ios/archive/Runner.xcarchive in Xcode and choose Distribute App.

Optional: certificate pinning

To make the apps accept only your server's certificate key, add its public-key pins to the build: --dart-define=API_CERT_PINS=<pin>,<backup-pin>. Always include a backup pin, or the apps stop working when your certificate's key changes. Each pin is the base64 SHA-256 hash of the certificate's public key, which this command prints:

openssl s_client -connect api.your-domain.com:443 -servername api.your-domain.com </dev/null \
  | openssl x509 -pubkey -noout | openssl pkey -pubin -outform der \
  | openssl dgst -sha256 -binary | openssl base64

Publishing on the stores

  • Account deletion: Google Play and the App Store require it for apps where people create accounts. Customers delete their account from the account screen. Riders delete theirs at the bottom of the Profile tab, after they finish their deliveries, hand in cash and get paid out; earnings below the payout minimum can be given up instead. Their documents, vehicle details and payout details are then removed. What either of them wrote or sent is erased too: order chat messages and images (shown as Removed at the customer's request, or the rider's), problem notes and photos, cancel or failed-delivery reasons, safety-report descriptions and photos, order, address, gift and dish notes, gate codes and gift recipients on their orders, the delivery photo of their orders, rating comments, support tickets and a customer's saved addresses. The street address on past orders is kept for receipts and tax records. Order safety timelines still verify and show it as removed at their request.
  • Privacy: each iOS app includes a privacy manifest (ios/Runner/PrivacyInfo.xcprivacy). Fill in Google Play's Data safety form and Apple's App Privacy answers to match what your platform collects (phone number, name, addresses, order history, and location for riders), and link your privacy policy (Settings → General → Legal).
  • Rider location: see Rider app for the location texts and the Google Play foreground-service declaration.
  • Minimum version: after publishing an update that older versions must not miss, raise the minimum version under Settings → App versions (Admin panel).

Languages in the apps

The apps include English, Bangla (Bengali) and Arabic, with right-to-left layouts for Arabic. Users pick from the languages switched on under Languages in the admin panel. Once more than one is on, each app shows a language choice:

  • Customer app: Account → Language.
  • Rider app: Profile → Language.
  • Restaurant app: Language in the kitchen board's device menu.

Picking Arabic switches the app to right to left straight away. Customers and riders keep their language on their account, so notifications follow it; the restaurant app keeps the choice on the device.

Times show on the 12-hour clock with AM/PM in every language, for example 3:05 PM. Printed tickets and receipts use Latin letters and digits whatever the app's language, since receipt printers often have no other characters. In Arabic, numbers, order numbers, addresses and amounts inside a sentence read in the right order.

To add another language, add it in the admin panel and translate it under Languages → Texts (on the page, or with Download JSON and Upload JSON). The apps load those texts when they start and when they come back to the screen after 5 minutes or more, so no new build is needed; texts not translated yet show in English. The same page changes any text of an existing language.

Developers can also build a language into the apps: each app keeps its texts in lib/localization/ and the shared texts in packages/biteway_core/lib/src/localization/core_translations.dart, as one map per language. After changing them, run UPDATE_TRANSLATION_CATALOG=1 flutter test test/translation_catalog_test.dart in the app, so the admin's Texts page lists the new texts (the test fails until you do).

The app your customers use to order. It lives in main/biteway-customer-app/.

What customers can do

  • Sign in with their phone number and a code, or with Google and Apple when you turn them on. With guest checkout on, they can order without an account.

  • Book a table, with a deposit when the restaurant asks for one, and order at the table by scanning its QR code.

🛵 Rider app

The app your delivery riders use. It lives in main/biteway-rider-app/.

What riders can do

  • Join: sign in with their phone number, fill in their profile and vehicle, and upload their documents. They can go online once you approve them under Riders in the admin panel. The sign-in screen shows the tagline "Deliver on your schedule"; change it under Languages → Texts in the admin panel.

  • Delivery speed: Saver and Express offers and deliveries carry a tag (Standard ones have none). With Settings → Extras → Give Saver deliveries a later window and batch them on, a Saver order may wait a few minutes for a second order from the same restaurant branch, so one trip carries both (Smart Saver).
  • Stay safe: an SOS button on every delivery, and incident reports.
  • Earnings: today's earnings, the history of deliveries and pay, cash to hand in, and payout requests.
  • Help: support tickets, also from a delivery.
  • Language: Profile → Language, once you offer more than one. Arabic shows the app right to left, and notifications follow the rider's choice.
  • Leave: delete the account from the Profile tab, once deliveries are finished, cash is handed in and earnings are paid out. Location and the app stores

The rider app uses the phone's location only while the rider is online, to offer nearby deliveries and show customers their rider on a map. It asks for "while using the app" access only, never "always":

  • Android keeps sharing while the rider uses a navigation app through a foreground service, with a notification ("You are online") shown the whole time.
  • iOS uses the location background mode, with the system's location indicator shown.

Going offline stops it. The texts the rider sees are in ios/Runner/Info.plist (NSLocationWhenInUseUsageDescription) and lib/localization/rider_translations.dart. If you change them, keep them true to what the app does: store reviewers compare them with the app.

Google Play asks about this when you publish (App content → Foreground service permissions):

  • Permission: FOREGROUND_SERVICE_LOCATION.
  • Task: location sharing while the delivery rider is online.
  • Video: a short screen recording showing the rider going online, allowing location, the "You are online" notification, a delivery with the navigation app open, and going offline.

In the Data safety form, location is precise, collected, shared (with the customer of the order the rider carries), required for riders, and used for app functionality.

App Store: in App Review Information → Notes, explain that location is used only while the rider is online and that the app asks for "While Using" access only. Give the reviewers an approved rider account and a backend they can reach.

🍳 Restaurant app

The app restaurants use to run their kitchen and front of house, on phones and tablets. It lives in main/biteway-restaurant-app/.

Signing in and setting up a device

Restaurant staff sign in with their email and password: the owner account you create with the restaurant, and, with the Restaurant Portal add-on, the team members the restaurant adds there. On first sign-in, the device is set up: which branch it serves, which station it is (the order lanes it shows and whether it chimes), a sound check, and its printers.

On a shared tablet, colleagues switch by picking their name and typing their personal PIN, without signing out.

Once you offer more than one language, the kitchen board's device menu has Language. Arabic shows the app right to left. The choice is kept on the device, so it stays the same for everyone who uses it.

What restaurants can do

  • Kitchen board: new, cooking, ready and finished orders in columns (in tabs on a phone), with each order's dishes and notes. Accept or reject new orders, and mark them ready. Late orders are highlighted.
  • Food waiting: with Settings → Extras → Warn when ready food waits for pickup on, ready orders show how long they have waited for the rider, highlighted when they wait too long, and staff get a push (Extras).
  • Saver orders and sister branches: Saver orders carry a Saver tag on the kitchen board and the order screen, and with Smart Saver on a ready Saver order may wait a few minutes for its rider (Smart Saver). With branch routing on, customers are sent to a less busy branch, and can move their order to a sister branch when this one is busy (Branch routing).
  • Split pizzas and the customer's journey: with Split-Pizza Studio on, a half-and-half pizza shows Left and Right blocks with each half's flavor and toppings, plus the whole-pizza toppings, on the kitchen board, the order screen and printed tickets (Split-Pizza Studio); with Live Kitchen Journey on, customers follow each status the kitchen sets as a stage of their order's journey (Live Kitchen Journey).
  • Group orders: with Group Meal Cart on, a group order's dishes are grouped under each member's name with a Group order · 3 people badge on the kitchen board and the order screen, and printed kitchen tickets print each name before that person's dishes (Group Meal Cart).
  • Order changes: when a dish is not available, propose a change that the customer accepts or declines.
  • Tables: the floor plan with each table free or busy. Open a check at a table, send rounds to the kitchen, serve, and take payment. Checks keep working without internet and catch up when the connection returns. If the server refuses an action, for example one for a table, till or check it doesn't know, syncing stops there with the reason, and the device keeps that action and the ones after it for the manager.
  • Till: open and close the till, with an X report while open and a Z report at closing.
  • Stock: switch a dish or option off when it runs out, and back on.
  • Inventory: ingredients, stock counts and deliveries from suppliers.
  • Bookings: table reservations by day, with new bookings to confirm.
  • Reviews: customer ratings, with replies.
  • Problem reports: problems customers reported with a delivered order, with the dishes, note and photos. Staff who reply to reviews get a notification and can add the restaurant's side once before the admin decides.
  • Shift report: today's numbers for the branch, or an earlier day.
  • Branch status: pause orders, or switch on busy mode for a set number of minutes when the kitchen is full.

🔌 API reference

Import the Postman collection to try every endpoint. Endpoints marked public need no token.

The API used by the Biteway Customer, Rider and Restaurant apps. Regenerate this file after changing routes: php artisan biteway:api-collection.

  1. Set the baseUrl variable to {APP_URL}/api/v1.

  2. Sign in with auth.otp.send, then auth.otp.verify (on a development server with the "log" text provider the code is in data.debug_code), and copy data.token into the token variable.

🧰 Troubleshooting and FAQ

When something goes wrong on the server, look first at Health in the admin panel, then at the newest file in storage/logs/. The log names the real error even when the page only says "Server Error".

Server and admin panel

"500 Server Error" right after uploading. storage/ or bootstrap/cache/ is not writable by the web server. Run the chown and chmod commands from Installation, then reload.

"Vite manifest not found", or the admin panel has no styles. public/build/ is missing: run npm ci && npm run build in biteway-backend (or on your computer, then upload public/build/).

"Class not found" or "vendor/autoload.php" errors. vendor/ is missing or incomplete: run composer install --no-dev --optimize-autoloader.

I can't sign in to the admin panel; the login page just reloads. The site is opened over plain http://, and the sign-in cookie is only sent over HTTPS. Add HTTPS, or, for a test only, set SESSION_SECURE_COOKIE=false in .env and run php artisan optimize. On localhost, http:// works.

I changed .env but nothing changed. The configuration is cached. Run php artisan optimize after every change to .env.

/install shows "Not Found". Biteway is already installed: the installer switches itself off. To install again from scratch, use an empty database and remove APP_KEY from .env.

Uploaded photos don't show. Run php artisan storage:link, and check that APP_URL in .env is the address you open the site with. If it stops with "Call to undefined function … exec()", your host blocks PHP's symlink(): in the biteway-backend folder, run ln -s ../storage/app/public public/storage in the host's terminal (SSH or cPanel Terminal), or ask your host to create public/storage.

Orders are not offered to riders, and notifications are not sent. The cron job or the queue worker is not running. Health shows which; Deployment shows how to start them.

Health says the queue worker is late ("Last job run 12 minutes ago" or "No job run yet"). Every minute the scheduler puts a heartbeat job on the queue, and the check fails when no worker has run one for 5 minutes.

  • "No job run yet" right after installing: start the worker and the cron job (Deployment), then wait a minute.
  • The scheduler check fails too: the cron job is not running, so no heartbeat is queued. Fix the cron job first.
  • Only the queue check fails: the worker stopped or is stuck. Run sudo supervisorctl status, check storage/logs/worker.log, and run php artisan queue:restart.
  • With QUEUE_CONNECTION=redis: check the Redis row in Health as well. If Redis does not answer, the worker can't take jobs.
  • The worker and the website must use the same cache (CACHE_STORE), because the heartbeat is stored there.

Health says Redis does not answer. Check REDIS_HOST, REDIS_PORT and REDIS_PASSWORD in .env, run sudo systemctl status redis-server, and check that PHP has the redis extension (php -m | grep redis). To stop using Redis, set CACHE_STORE, QUEUE_CONNECTION and SESSION_DRIVER back to database, then run php artisan optimize.

Search results are out of date, or Meilisearch is down.

  • New or renamed dishes are not found: the queue worker sends changes to Meilisearch. Check the queue worker in Health, then click Reindex now under Integrations → Search (or run php artisan biteway:search:reindex).
  • Health warns that the counts differ: run the reindex. It also puts right restaurants or dishes deleted directly in the database, or changed while Meilisearch was down.
  • Health says "No answer from http://127.0.0.1:7700": Meilisearch is not running, or MEILISEARCH_HOST is wrong. Until it answers, the database answers searches, so customers can still search, and each failed search is written to storage/logs/. Start Meilisearch, then reindex.
  • Health says "Cannot read the index counts", or the log shows invalid_api_key: MEILISEARCH_KEY doesn't match the key Meilisearch was started with. Fix it in .env and run php artisan optimize.
  • To stop using Meilisearch: choose MySQL full-text or Simple matching under Integrations → Search.

A broadcast says "Sent, but nobody was reached", or people are skipped with "Push not set up". Open the broadcast under Content → Broadcasts: its page lists why people were skipped.

  • Push not set up: the server has no Firebase key. Add it under Firebase, then send a new broadcast. Until then a broadcast only fills the app's notification list.
  • No app with notifications on: those people have no signed-in app that allows notifications.
  • Switched promotions off: those customers chose not to get offers and promotions.
  • Sending stopped: sending failed; the newest file in storage/logs/ names the error.

A scheduled broadcast didn't go out.

  • Still Scheduled after its time: the cron job is not running. Check Health, and see Deployment.
  • Sending, but the counts don't move: the queue worker is not running. Health shows it.
  • Another broadcast is still sending: only one sends at a time, so this one starts when that one finishes.
  • The time is read in the platform time zone under Settings → Localization & currency.

Customers don't get their sign-in code. Check the text message provider under Settings → Sign-in and its keys under Integrations. Firebase Phone Authentication needs the Firebase project ID under Integrations → Live updates, and on the Customer Website also the Firebase Web API key. The provider's own dashboard shows whether the message was sent and why it failed (for example a sender number not allowed in that country). On a test server, the provider Server log only writes the codes to storage/logs/ instead of sending them; it is not offered on a live server.

Emails don't arrive. MAIL_MAILER=log writes emails to storage/logs/ instead of sending them. Set your SMTP details (Deployment) and run php artisan optimize.

An update shows "Failed, not put back", or Roll back is missing.

  • Roll back shows only on the latest applied update. Roll back the newer ones first.
  • "Failed, not put back" means the update failed and its files and database could not be restored, so the site may be partly on the new version. Restore the site and database from your own backup, then contact support. Until then, older updates can't be rolled back.
  • "Another update or rollback is running" means one is still in progress. Wait for it to finish, then try again.

Health warns that the newest backup is older than 48 hours. No backup was made in the last two days in the backup folder. Turn on Back up every day under Settings → General → Backups and check that the cron job runs, or run php artisan biteway:backup (Backups and restore). Health only counts backups in the default folder (storage/app/backups, or BITEWAY_BACKUP_PATH), not those saved elsewhere with --to. If Health says the folder can't be written, make it writable for the web server user.

After moving or restoring the site, payment keys are missing and payout accounts show nothing. The site's APP_KEY differs from the one the keys were saved with, so they can't be read. Put the original APP_KEY back in .env and run php artisan optimize. If the backup held .env, the restore saved it as .env.from-backup: copy its APP_KEY line into .env. Without the original key, enter the payment and provider keys again and ask restaurants and riders to add their payout accounts again.

A payment stays "pending". The gateway could not reach your webhook. Copy the webhook URL shown on the Payments page into the gateway's dashboard exactly, and make sure the site has HTTPS.

Apps

The app stops at launch with "API_BASE_URL must be an https:// address". Release builds only accept an HTTPS backend. Build with --dart-define=API_BASE_URL=https://api.your-domain.com.

The app can't connect to the backend.

  • Open https://api.your-domain.com/api/v1/config in a browser: it should show the platform's settings as JSON. If not, fix the server first.
  • Check that the build used the right API_BASE_URL, with no /api at the end.
  • Android blocks plain http:// addresses, except in debug builds for a backend on your computer (10.0.2.2, 127.0.0.1 and localhost, as described in Mobile apps). Anything else needs HTTPS.

"A new version of the app is available. Update it to keep using the app." The app is older than the minimum version under Settings → App versions. Install the newer build, or lower the minimum version.

No push notifications.

  • Each app needs its Firebase files (Mobile apps), and the server needs the service-account key under Firebase.
  • iOS also needs the APNs key uploaded in the Firebase console, and a real iPhone: the simulator gets no pushes.
  • The user must have allowed notifications on the phone.

The map is empty or grey. With Google Maps chosen, the app's key is missing or restricted to another package name or bundle ID. Check the key in android/secrets.properties and ios/Flutter/Secrets.xcconfig, or choose map tiles under Integrations → Maps.

"Continue with Google" fails on iPhone. The iOS client ID and URL scheme are missing from ios/Flutter/Secrets.xcconfig (Mobile apps), or the client IDs under Integrations → Google and Apple sign-in don't match your apps.

The rider's location stops when the screen is off. The rider must allow location "while using the app" and stay online; on Android, battery savers can stop the app. Ask riders to exclude the rider app from battery optimization in the phone's settings.

A rider can't delete their account. The app says why: a delivery is still in progress, cash has not been handed in, earnings have not been paid out, or a payout is on its way. Once that is settled, deleting works. Earnings below the payout minimum can't be paid out, so the app offers to give them up; given-up earnings appear as forfeited_rider_earnings in the trial balance of the Finance report.

Questions

Can I use Biteway without Firebase? Yes. Without Firebase the apps ask the server for updates instead of receiving them instantly, there are no push notifications (the in-app inbox still fills), and sign-in codes go by Twilio or BulkSMSBD.

Why are PDF receipts and invoices in English when the app is in Bangla or Arabic? The PDF font can't print Bangla or lay out right-to-left text, so PDFs in those languages (and others with such scripts) are made in English. Everything else stays in the user's language.

Can I change the currency after installing? Only before the first order. Every amount is stored in the platform currency.

Do I need the Customer Website or the Restaurant Portal? No. They are optional add-ons, sold separately. Without them, customers order in the customer app, and restaurants work in the restaurant app while you add restaurants and their menus in the admin panel.

💬 Support

Support is given through CodeCanyon: open the Support tab on the Biteway item page and send your question there. Item support covers questions about how Biteway works, help with problems and bugs in the item, and help with the third-party parts included with it. It does not cover installing it on your server for you, customizing it, or building new features.

What to send

So we can help quickly, include:

  • The Biteway version: the admin panel shows it at the bottom of the menu and on the Health page.
  • What you did, what you expected, and what happened instead, with screenshots.
  • For a server problem: the error from the newest file in storage/logs/, and what Health shows.
  • For an app problem: the app, the phone and its system version, and whether it happens on a test build or a store build.

Never send passwords, API keys, .env files, keystores or your customers' personal data.

Before you write

Many questions are answered in Troubleshooting and FAQ. Checking Health in the admin panel and the newest log file in storage/logs/ often shows the cause straight away.
